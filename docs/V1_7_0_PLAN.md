# 1.7.0 设计与实现记录

正式版本配置为 `1.7.0`，首个真机测试候选包为 `1.7.0-dev.1`，versionCode `10700`。快捷开关、快捷动作、备份、叠卡组件、可选捕获监视窗及配置展示分组均已实现；没有发布线上版本。真机验证记录见 [验证与使用说明](V1_7_0_VERIFICATION.md)。功能实现前回退点为 `pre-v1.7.0-features-20261113`。

## 快捷捕获开关

使用 Android 7.0 起提供的 TileService。单击直接切换全局捕获，不要求先打开主页面；开启、关闭、暂不可用有明确状态。Android 13 起可以请求用户添加磁贴，旧版引导用户在快捷设置编辑区添加，最终添加由用户决定。

必须先收敛 HomeFragment、HookStatusManager、MessengerService 分散的捕获状态和通知入口，保证磁贴、首页与后续监视窗一致。保留现有语义：主应用及磁贴控制全局；注入目标进程的悬浮窗仍只控制所在进程。不能在 TileService 生命周期结束时自动关闭捕获，也不能将“模块可用”与“当前捕获已开启”混为同一状态。

## 独立的“快捷动作”页

收藏继续保存捕获记录，快捷动作保存用户整理好的可执行内容。入口包括捕获详情、收藏详情、手工输入 Scheme / Intent URI，以及后续动作文件导入。用户无需先抓取一次才能创建动作。普通 Scheme 与 Intent URI 需要明确区分、解析校验；解析失败保留输入并给出具体错误。

动作至少包含稳定 ID、昵称、私有持久化图标、目标内容、动态参数定义、执行模式与必要来源信息。目标内容沿用完整 Intent 载荷机制，不能只保存 toUri() 结果而丢掉自定义参数；来源限制与错误提示沿用现有重放逻辑。不要为了桌面入口重新实现一套解析或执行链路。

复用 ShortcutPayloadStore / ShortcutLaunchCoordinator 的载荷及执行能力，逐步让已有快捷方式与新动作共用它；保留旧快捷方式 ID 和载荷读取路径。动作保存自己的快照，删除收藏不得破坏已经保存的动作或桌面入口。

每个桌面小组件保存自己的动作 ID 列表和顺序，允许不同组件显示不同内容。收藏、动作、组件中是否展示是三个不同概念，不能用收藏记录的一个全局布尔字段代替。

## 桌面叠卡小组件

先验证 RemoteViews + StackView 原型，再确定视觉：昵称、图标、简短说明，上下滑动切换、点击执行。每个组件独立选择动作并排序，支持调整尺寸及后续重新配置。动态参数仍通过现有透明 Activity 弹窗输入，普通 / Shizuku / Root 等执行模式沿用现有协调逻辑。

StackView 原生提供上下滑动叠卡，但不能据此断定参考应用使用同一方案，或保证各桌面的动画完全一致。验收须覆盖不同桌面、尺寸、明暗主题、多组件、重启和应用进程被杀后的恢复；重点区分滑动与点击，不能滑动时意外执行动作。原型未达到手感要求前不承诺成品效果。

## 可选捕获监视窗

由主应用提供独立、默认关闭的悬浮监视窗，用户开启后且全局捕获正在进行时，在其他应用中显示本次新增数量、最后捕获的应用 / 时间、连接数量，提供暂停与返回详情。它使用主应用实际收到并提交的记录，不能把目标进程已经抓到但尚未送达的数据误报为已收录。按用户追加要求，停止或暂停捕获立即收起窗口并结束捕获会话服务；继续捕获从首页或快捷设置磁贴开启。

不要复用目标进程注入悬浮窗作为全局状态来源。关闭监视窗与停止捕获分开处理，回到主页面时可以收起窗口。悬浮权限按需请求，拒绝后基础捕获不受影响；后台存活按对应 Android 版本规范设计，可提供持续通知入口作为替代。

Reqable 的具体实现尚未确认。PiP 提供系统管理的窗口，但主要面向视频、通话和导航，布局与交互受限制；如果需求是拖动吸附、显示多条捕获并直接操作，普通悬浮监视窗更适合。不能仅凭外观断定参考应用采用哪种方式。

## 小项与实施顺序

配置页“所有”列表当前按配置存储顺序加载，因此历史追加的 Intent 项落在 Scheme 后。建议只对展示列表按类别稳定分组，同类别保留原顺序，不改捕获记录时间顺序、不改 Hook 执行配置或开关状态。

推荐顺序：统一全局捕获状态与磁贴 → 快捷动作及手工导入 → 叠卡原型与组件 → 可选监视窗。每一步独立提交并验证已有快捷方式、动态参数及自定义参数重放，避免把新功能与系统框架 Hook 修改绑在同一次测试中。

额外值得考虑：动作导出 / 备份、多个动作批量导入、分组与拖动排序。涉及完整第三方自定义对象的导入导出，必须保留来源和现有限制，不能把 URI 导入描述成可以凭空恢复任意自定义类。
